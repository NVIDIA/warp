Array Function Overrides#

Array subclasses and wrappers can implement __warp_function__ to intercept supported host Python operations, such as launch() or clone(). The hook runs before Warp specializes a kernel, submits work, or converts a source array. It receives the original operands and can return an alternative result, observe the operation by delegating to Warp, or decline it.

The name follows PyTorch’s __torch_function__ and NumPy’s __array_function__ conventions. It refers to host Python APIs and does not change compiled @wp.func definitions, kernel-side function calls, or wp.Function overload resolution.

Enabling Array Function Overrides#

Array function overrides are disabled by default. Applications that use this protocol must explicitly enable it:

import warp as wp

wp.config.enable_array_function_overrides = True

Enable this at startup, before saving or importing aliases of supported Warp APIs. This includes importing integrations that save or wrap Warp functions. A compatibility shim can retain a native function even when application code later calls through the warp module. While disabled, registered Warp bindings call their native functions directly, including array initialization. Enabling the flag installs cached forwarding wrappers and adds work even when operands have no custom hook.

Activation switches known registered bindings in loaded Warp modules, including public exports and internal aliases, together with the explicitly registered array.__init__ binding. Unrelated external patches are preserved. Aliases saved in application variables, containers, or class attributes before activation retain their native outer entrypoints. Those native bodies may still call other helpers whose bindings are now wrapped. Obtain aliases after enabling overrides when you need the outer operation to be intercepted reliably.

Wrapper aliases saved while enabled retain their identity and honor subsequent flag changes. Disabling restores native registered Warp bindings without replacing wrapper references held by applications. Normal Python function pickling is supported for the currently exported callable; aliases to the inactive native or wrapped version may fail because the module now exports the other version.

The flag is process-wide. Change it only at startup or between tracing sessions, without concurrent calls. Switching bindings does not provide session isolation or an atomic transition across all APIs. Hooks automatically suppress overrides in the current execution context while they run. Enabling the flag does not add hooks to graph replay or saved launch-command execution.

Defining a Hook#

Define the hook as a synchronous class method; a plain instance-method hook raises TypeError with guidance to use @classmethod:

@classmethod
def __warp_function__(cls, func, types, args=(), kwargs=None):
    ...

cls is the concrete participating type, including when it inherits the hook. func is the registered Warp wrapper and can be used as a registry key. For unpatched Warp bindings, it is also the public callable and can be compared with wp.launch. Aliases obtained after enabling overrides also dispatch; aliases saved before activation keep their native outer entrypoints. types is the tuple of unique types with active overrides, in dispatch order. It excludes ordinary arrays and other objects without an override.

args and kwargs preserve the caller’s positional tuple and supplied keyword arguments. Warp does not insert omitted defaults, unwrap operands, or replace them with copies. Any result other than the singleton NotImplemented finishes the operation and is returned unchanged, including None and False. Exceptions propagate immediately.

Return NotImplemented before making changes if the hook cannot handle the function or participating types. Warp tries the next candidate, then executes its native implementation once if every candidate declines. Subclasses without an override retain native behavior. The neutral hook inherited from Warp’s array base also returns NotImplemented; super().__warp_function__(...) defers to the superclass hook rather than executing Warp’s implementation.

A declining hook must leave operands, argument containers, and tracing state unchanged. Warp cannot roll back mutations, submitted work, or capsules consumed by an override.

Native fallback uses the original operands and applies the usual validation. A wrapper that Warp cannot otherwise accept must adapt its operands while handling the call. Returning NotImplemented does not unwrap it.

Delegating to Warp#

Call the supplied func directly to invoke Warp’s implementation. Overrides are automatically suppressed while a hook runs, so delegation does not call the hook again. For example, this subclass records successful operations:

import warp as wp

wp.config.enable_array_function_overrides = True


class ObservedArray(wp.array):
    calls = []

    @classmethod
    def __warp_function__(cls, func, types, args=(), kwargs=None):
        if not all(issubclass(t, ObservedArray) for t in types):
            return NotImplemented

        result = func(*args, **({} if kwargs is None else kwargs))

        cls.calls.append(func)
        return result


x = ObservedArray([1.0, 2.0], dtype=wp.float32, device="cpu")

y = wp.clone(x)
wp.copy(dest=x, src=y)
assert ObservedArray.calls == [wp.clone, wp.copy]

All supported Warp calls made inside a hook use their native implementations, including calls to different functions or with different operands. These calls do not try other operand hooks. A hook handling mixed types must coordinate their behavior explicitly, or return NotImplemented before doing work so Warp can try the next candidate for the original call. After executing a native operation, return its result rather than NotImplemented to avoid running the operation again during fallback.

Suppression is restored after the hook returns or raises an exception. It affects the current execution context rather than the process-wide flag and follows Python’s normal context inheritance rules: a context copied inside a hook retains suppression. Hooks must be synchronous. This isolation does not change Warp’s runtime, tape, or capture concurrency guarantees.

Warp suppresses hooks throughout every selected native implementation, including when no candidate participates. As a result, a call to clone produces one event; its internal allocation and copy do not produce more events. Likewise, launch_tiled is observed under its own identity without an additional launch event. Native array initialization suppresses hooks while it prepares the array. Subclass authors should attach metadata before making supported Warp calls in their own initialization code; those calls can invoke hooks once the native initializer has returned.

Operand Discovery and Ordering#

Warp resolves __warp_function__ on the operand’s type. Instance attributes are not consulted. An absent hook or one set to None does not participate; a non-callable hook raises TypeError.

Direct supplied arguments are visited in the function’s declared parameter order, regardless of keyword insertion order. For launch and launch_tiled, Warp also recursively inspects exact list and tuple containers in inputs, outputs, adj_inputs, and adj_outputs. Discovery detects cycles and does not descend into an object with an active hook. It does not iterate generators or custom sequences, traverse dictionaries or struct fields, or inspect arbitrary object attributes. A custom argument container can implement its own hook. Discovery does not make a nested container a valid native kernel argument.

Each concrete participating type is called at most once. Two subclasses that inherit the same user hook participate separately. On encountering a new type, Warp inserts it before the first existing type that is its strict superclass, or appends it if there is no such superclass. Actual Python inheritance controls this priority; virtual ABC registration does not. Encountering Base, Other, then Child where Child inherits Base produces (Child, Base, Other).

For copy, the destination precedes the source. For launches, forward inputs precede forward outputs, then adjoint inputs and adjoint outputs. Normal Python call errors such as duplicated parameters are raised before any hook runs.

Covered APIs#

The following public functions support the protocol:

Functions

Operands and behavior

launch(), launch_tiled()

Direct arguments and the four launch argument sequences.

copy(), clone()

Source and destination operands; delegated copy still returns None.

empty_like(), zeros_like(), ones_like(), full_like()

The template array and other direct arguments.

from_numpy()

Direct arguments, including a NumPy subclass with a hook.

from_torch(), to_torch()

Direct source and explicit gradient arguments; hooks run before an optional PyTorch import or conversion.

from_dlpack(), to_dlpack()

Direct arguments; hooks run before requesting or consuming a capsule.

utils.array_scan()

Input, output, and an explicit temp_storage array; delegated calls write into the output and return None.

utils.array_sum(), utils.array_inner()

Input arrays and an explicit out array; retain the native host-value or output-array return form.

utils.radix_sort_pairs(), utils.segmented_sort_pairs()

Keys, values, and provided segment-index arrays; delegated calls retain in-place sorting and scratch-storage requirements.

utils.runlength_encode()

Input, run-value, run-length, and explicit run_count arrays; retain the integer or count-array return form.

Plain NumPy arrays and PyTorch tensors do not acquire this hook automatically. Discovery never reads array contents or invokes __array__, __dlpack__, or an array-interface property. A delegated conversion retains Warp’s existing device, stream, gradient, lifetime, and return_ctype behavior. Decide whether to handle a DLPack call before requesting its data; consume a capsule only once.

Utility hooks run before the native body inspects array metadata or records an API Capture (APIC) operation. Delegation retains each utility’s existing storage, mutation, and return-value behavior. Internal allocation, copy, and readback calls do not generate additional hook events for that utility call. Existing capture restrictions still apply: non-empty APIC reductions require an explicit out, and non-empty APIC run-length encoding requires an explicit run_count.

Storage, Mutation, and Results#

The hook receives the actual objects, preserving repeated-object identity and storage aliases. Delegation must preserve destination storage and ownership, especially for copy and kernel launches. Replacing a destination with a new allocation changes what the caller observes. A kernel can mutate an array passed through inputs; the launch input and output groups are not complete read and write declarations.

Warp does not preserve subclass types or copy arbitrary metadata into results. An override owns that policy. Fresh allocations can receive new metadata; conversions sharing storage must retain the source owner and alias relationship. Generic reconstruction or reassignment of __class__ is not a supported wrapping recipe. Subclass inputs use their registered Warp array family for native validation and generic specialization while retaining their original Python object and gradient descriptor. Kernel annotations continue to use Warp’s base array types, such as wp.array[float]. See Array subclass compatibility for the full subclass contract.

Coverage Limits#

The protocol applies to covered host functions. Array constructors, methods such as .numpy(), .to(), .zero_(), and .reshape(), Python operators, wp.map, utilities outside the explicit coverage table, Paddle and JAX integrations, and mesh and volume APIs are outside this set. Internal calls to covered functions outside a suppressed native implementation may dispatch, but they do not provide a stable hook for the outer operation. Factories such as wp.zeros(shape=...) have no array operand from which to select a hook and are not registered.

Compiled kernel operations and calls to @wp.func inside kernels do not dispatch. With record_cmd=True, a launch hook observes construction of a Launch object rather than its later execution. Launch.launch(), CUDA graph replay, and API capture replay do not invoke these host hooks. Tracing systems that need array-free operations, uncovered methods, command execution, or replay must provide their own instrumentation.
